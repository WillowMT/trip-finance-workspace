# Build Specification: Shared-Workspace Finance Tracker on Cloudflare D1

## Purpose

Build a reusable, Cloudflare-native version of this finance tracker for any group to use immediately.

It must retain the useful behaviour of the Vietnam finance tracker—ledger entry, payments, splits, batch entry, CSV import with review, analytics, netting/offsets, ranking, export, deletion confirmation, and audit history—while replacing fixed trip data and Neon/Postgres with:

- one **shared editable workspace link** per group;
- Cloudflare **Worker + D1** as the application and database backend;
- first-run onboarding for workspace name, people, currencies, and defaults;
- configurable workspace data rather than source-code constants;
- **no Telegram webhook, bot token, outbound notification, or Telegram event** in the initial release;
- an audit trail that covers every financial and workspace-configuration mutation.

This document is the implementation contract. Build a new project from it rather than converting the deployed Vietnam project in place.

---

## Non-negotiable product rules

1. **One shared editor link.** Anyone who holds the complete link can use one workspace immediately—there are no accounts, invitations, usernames, roles, or editor-name fields.
2. **All shared-link users can edit.** They may create transactions, create payments, create splits/imports/offsets, and delete or archive configurable workspace data where safe.
3. **Every mutation is auditable.** Transaction and configuration create/update/archive/restore/delete actions must write an audit row in the same D1 statement batch/transaction as the mutation.
4. **Audit rows are application-append-only.** The Worker never exposes audit write/update/delete endpoints. D1 triggers reject direct `UPDATE` or `DELETE` statements against `audit_log` from the application connection.
5. **Audit detail is complete.** An audit entry has entity type/id, action, timestamp, workspace id, whole JSON `before_json` and/or `after_json`, and the literal `actor_label = 'shared workspace editor'`.
6. **No misleading identity.** A shared link cannot prove which person used it. The UI must never claim that an audit entry identifies an individual.
7. **No silent history breakage.** A person or currency referenced by historical transactions is archived, not physically deleted. A historical transaction may be deleted only through the delete endpoint, which audits the whole row.
8. **Review precedes writes.** Natural language, CSV, split, batch, offset, and ordinary-entry screens may prepare drafts, but only an explicit review confirmation writes to D1.
9. **Telegram is disabled by design.** There is no Telegram configuration, secret, URL, import, outbound `fetch`, or event emitter in the first release.
10. **Workspace isolation is server-enforced.** Never trust a workspace id received from HTML or JSON. Resolve the workspace only from the shared-link secret and add that id to every D1 read/write predicate.

## Architecture decision

### Recommended stack

- **Cloudflare Worker** serving the static single-page application and `/api/*` JSON routes.
- **Cloudflare D1** for all persistent application data.
- Vanilla HTML/CSS/JavaScript (reuse the existing visual patterns and review-modal conventions).
- Node’s built-in test runner plus Miniflare/Wrangler D1 test database.
- Optional R2 export/archive support is a later feature. Initial backups download JSON/CSV generated by the Worker; no external webhook is required.

Do not use Neon, Postgres, `@neondatabase/serverless`, `DATABASE_URL`, Pages Functions, or the Telegram bot in the new project.

### Why a Worker instead of Pages Functions

A single Worker has one place to enforce shared-link secret resolution, API authorization, static routing, security headers, and D1 bindings. It makes deployment and local D1 testing one coherent unit. It also avoids accidentally leaving a static Pages route outside workspace authorization.

### Workspace link format

Use a high-entropy opaque secret, not a guessable id:

```text
https://<worker-domain>/w/<base64url-32-byte-secret>
```

Rules:

- Generate the secret with `crypto.getRandomValues`, 32 random bytes, base64url encoded.
- Store **only a SHA-256 hash** of the secret in D1 (`workspace_secret_hash`).
- The raw secret appears only in the browser URL; never persist it in D1 logs, audit JSON, error messages, analytics, or console output.
- Every workspace request extracts `/w/:secret`, hashes it, finds one active workspace, and passes its internal `workspace_id` to handlers.
- Never use the numeric `workspace_id` as authorization.
- The UI should provide a clear “Copy shared link” control and warn: “Anyone with this link can edit this workspace.”

No recovery mechanism is promised in v1. Losing the only shared URL loses normal access. The implementation may later add a separately protected owner/recovery capability, but must not fabricate one now.

## First-run onboarding

### Entry page

`/` is a landing page with one primary action: **Create shared workspace**. It must not present the tracker UI before a workspace exists.

### Wizard steps

1. **Name the workspace**
   - Required, trimmed 1–100 characters.
   - Examples may be “Bangkok roommates”, “Japan trip”, or “Friday football group”; no geographic assumption in the actual data model.

2. **Add people**
   - Require at least two active people.
   - Each display name is 1–80 characters, unique case-insensitively inside this workspace.
   - Allow add/remove rows before confirmation.

3. **Choose currencies and default**
   - Require at least one ISO-4217-style code (`^[A-Z]{3}$`) or a documented controlled list.
   - The user selects one default currency from enabled currencies.
   - Do not pre-fill only VND/SGD/USD/MYR. Reasonable examples are allowed, but users may remove them before submit.

4. **Confirm**
   - Show the created workspace name, people, currencies, and default currency.
   - On confirm, call `POST /api/onboarding` exactly once with idempotency protection or a disabled confirm button.
   - The Worker creates the workspace and all initial configuration in one D1 batch, then responds with the raw shared link exactly once.

### Onboarding audit records

Creation must create audit rows for:

- workspace creation (`workspace`, `create`)
- each person creation (`person`, `create`)
- each currency creation (`currency`, `create`)
- settings creation (`workspace_settings`, `create`)

These are normal audit entries. Do not skip them just because onboarding happens in one operation.

## D1 schema and migrations

Put migrations in `migrations/` and use Wrangler D1 migrations. Use a dedicated migration per conceptual change. Never edit an already-applied production migration.

### Core tables

```sql
-- migrations/0001_core.sql
PRAGMA foreign_keys = ON;

CREATE TABLE workspaces (
  id INTEGER PRIMARY KEY,
  secret_hash TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL CHECK (length(trim(name)) BETWEEN 1 AND 100),
  is_active INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0, 1)),
  created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
);

CREATE TABLE workspace_people (
  id INTEGER PRIMARY KEY,
  workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
  display_name TEXT NOT NULL COLLATE NOCASE CHECK (length(trim(display_name)) BETWEEN 1 AND 80),
  is_archived INTEGER NOT NULL DEFAULT 0 CHECK (is_archived IN (0, 1)),
  created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  UNIQUE(workspace_id, display_name)
);

CREATE TABLE workspace_currencies (
  id INTEGER PRIMARY KEY,
  workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
  code TEXT NOT NULL CHECK (code GLOB '[A-Z][A-Z][A-Z]'),
  is_default INTEGER NOT NULL DEFAULT 0 CHECK (is_default IN (0, 1)),
  is_archived INTEGER NOT NULL DEFAULT 0 CHECK (is_archived IN (0, 1)),
  created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  UNIQUE(workspace_id, code)
);

CREATE UNIQUE INDEX one_default_currency_per_workspace
ON workspace_currencies(workspace_id)
WHERE is_default = 1 AND is_archived = 0;

CREATE TABLE workspace_settings (
  workspace_id INTEGER PRIMARY KEY REFERENCES workspaces(id),
  categories_json TEXT NOT NULL DEFAULT '[]' CHECK (json_valid(categories_json)),
  small_amount_guard_json TEXT NOT NULL DEFAULT '{}' CHECK (json_valid(small_amount_guard_json)),
  created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
);

CREATE TABLE transactions (
  id INTEGER PRIMARY KEY,
  workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
  occurred_on TEXT NOT NULL CHECK (date(occurred_on) IS NOT NULL),
  entry_kind TEXT NOT NULL CHECK (entry_kind IN ('debt', 'payment', 'split', 'offset', 'import')),
  topic TEXT NOT NULL CHECK (length(trim(topic)) BETWEEN 1 AND 200),
  category TEXT NOT NULL CHECK (length(trim(category)) BETWEEN 1 AND 80),
  creditor_person_id INTEGER NOT NULL REFERENCES workspace_people(id),
  debtor_person_id INTEGER NOT NULL REFERENCES workspace_people(id),
  amount_minor INTEGER NOT NULL CHECK (amount_minor <> 0),
  currency_code TEXT NOT NULL CHECK (currency_code GLOB '[A-Z][A-Z][A-Z]'),
  notes TEXT,
  import_group_id TEXT,
  is_deleted INTEGER NOT NULL DEFAULT 0 CHECK (is_deleted IN (0, 1)),
  created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  CHECK (creditor_person_id <> debtor_person_id)
);

CREATE INDEX transactions_workspace_date_idx
ON transactions(workspace_id, occurred_on DESC, id DESC);
CREATE INDEX transactions_workspace_pair_idx
ON transactions(workspace_id, debtor_person_id, creditor_person_id, currency_code)
WHERE is_deleted = 0;

CREATE TABLE audit_log (
  id INTEGER PRIMARY KEY,
  workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
  entity_type TEXT NOT NULL,
  entity_id TEXT NOT NULL,
  action TEXT NOT NULL CHECK (action IN ('create', 'update', 'archive', 'restore', 'delete')),
  actor_label TEXT NOT NULL DEFAULT 'shared workspace editor',
  before_json TEXT CHECK (before_json IS NULL OR json_valid(before_json)),
  after_json TEXT CHECK (after_json IS NULL OR json_valid(after_json)),
  occurred_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
);

CREATE INDEX audit_log_workspace_recent_idx
ON audit_log(workspace_id, occurred_at DESC, id DESC);
CREATE INDEX audit_log_workspace_entity_idx
ON audit_log(workspace_id, entity_type, entity_id, id DESC);
```

### Amount representation

Store amounts as `amount_minor INTEGER`, never binary floating point.

- Keep a currency minor-unit map in Worker source (e.g. VND `0`, USD/SGD/THB `2`, JPY `0`) and validate/conform values at the HTTP boundary.
- The API accepts a decimal string such as `"123.45"`, validates it against the selected currency precision, then converts it to `amount_minor`.
- APIs return both `amount_minor` and formatted/display-ready information only when needed; calculations always use `amount_minor`.
- Debt is a positive amount; payment and offset entries are negative amounts on the same creditor/debtor direction. Do not reverse the relationship to encode payment.

### Cross-workspace integrity

D1 foreign keys alone do not prove that a selected person/currency belongs to the same workspace. Every write handler must query/validate all referenced person ids and currency code under the resolved workspace id before inserting. Add tests that attempt cross-workspace ids and assert a 404/400 plus no write.

### Audit triggers

Create audit triggers for `workspaces`, `workspace_people`, `workspace_currencies`, `workspace_settings`, and `transactions`.

Requirements:

- Use `AFTER INSERT`, `AFTER UPDATE`, and `AFTER DELETE` triggers for every auditable table.
- The insert trigger writes `action = 'create'`, `before_json = NULL`, `after_json = json_object(...)` containing **every stored column relevant to the row**.
- The delete trigger writes `action = 'delete'`, `before_json = json_object(...)`, `after_json = NULL`.
- Update triggers determine `archive`/`restore` when `is_archived` or `is_deleted` changes; otherwise use `update`.
- Snapshot the full row explicitly. SQLite has no Postgres `to_jsonb(NEW)`, so each trigger must list all columns. This list is part of the migration review checklist: when adding a table column, update every audit trigger and its test in the same change.
- `workspaces.secret_hash` must never be written to audit JSON. The audit log must not become a source of workspace capabilities or hashes.
- Do not audit changes to `audit_log` itself as ordinary audit events.

Example shape for a transaction insert trigger:

```sql
CREATE TRIGGER audit_transactions_insert
AFTER INSERT ON transactions
FOR EACH ROW
BEGIN
  INSERT INTO audit_log (
    workspace_id, entity_type, entity_id, action, before_json, after_json
  ) VALUES (
    NEW.workspace_id,
    'transaction',
    CAST(NEW.id AS TEXT),
    'create',
    NULL,
    json_object(
      'id', NEW.id,
      'workspace_id', NEW.workspace_id,
      'occurred_on', NEW.occurred_on,
      'entry_kind', NEW.entry_kind,
      'topic', NEW.topic,
      'category', NEW.category,
      'creditor_person_id', NEW.creditor_person_id,
      'debtor_person_id', NEW.debtor_person_id,
      'amount_minor', NEW.amount_minor,
      'currency_code', NEW.currency_code,
      'notes', NEW.notes,
      'import_group_id', NEW.import_group_id,
      'is_deleted', NEW.is_deleted,
      'created_at', NEW.created_at,
      'updated_at', NEW.updated_at
    )
  );
END;
```

### Audit-log protection triggers

```sql
CREATE TRIGGER audit_log_reject_update
BEFORE UPDATE ON audit_log
BEGIN
  SELECT RAISE(ABORT, 'audit log is append-only');
END;

CREATE TRIGGER audit_log_reject_delete
BEFORE DELETE ON audit_log
BEGIN
  SELECT RAISE(ABORT, 'audit log is append-only');
END;
```

This protects against Worker/application-level edits. Document the honest boundary in the UI/help text and README: a Cloudflare account/database owner can change migrations, replace triggers, or destroy a database. D1 alone cannot make an account owner unable to alter their own database. If tamper evidence beyond that boundary is required later, send a signed append-only event copy to a separately controlled system.

## API contract

All workspace-scoped endpoints live under the capability path:

```text
/w/:secret/api/...
```

The Worker resolves `:secret` before routing into workspace handlers. Do not put raw secret values into API bodies, query strings, error messages, or CORS headers.

### Read endpoints

- `GET /w/:secret/api/bootstrap`
  - Returns workspace display data: name, active/archived people, currencies, settings, and feature flags.
- `GET /w/:secret/api/transactions?limit=&cursor=&include_deleted=`
- `GET /w/:secret/api/analytics?person_id=&currency=`
- `GET /w/:secret/api/ranking`
- `GET /w/:secret/api/offset-suggestions`
- `GET /w/:secret/api/audit?limit=&cursor=&entity_type=&entity_id=`
- `GET /w/:secret/api/export?format=json|csv`

All read responses must send `Cache-Control: no-store` because the same shared URL is a capability and ledger data changes live.

### Configuration mutations

- `POST /w/:secret/api/people` — create person
- `PATCH /w/:secret/api/people/:id` — rename/archive/restore person
- `POST /w/:secret/api/currencies` — create enabled currency
- `PATCH /w/:secret/api/currencies/:code` — choose default/archive/restore currency
- `PATCH /w/:secret/api/settings` — update categories/guard settings
- `PATCH /w/:secret/api/workspace` — rename workspace

For all `PATCH` routes, use an allowlist of editable fields. Reject arbitrary JSON-to-SQL updates. Configuration removal defaults to archive. Restore is explicit and auditable.

### Financial mutations

- `POST /w/:secret/api/transactions/preview`
  - Validates a normal debt/payment draft; writes nothing.
- `POST /w/:secret/api/transactions`
  - Accepts only a reviewed normal debt/payment payload; creates one transaction.
- `POST /w/:secret/api/transactions/:id/preview-edit`
  - Validates a requested edit against the current active transaction and writes nothing.
- `PATCH /w/:secret/api/transactions/:id`
  - Accepts only the reviewed allowed-field payload, rechecks that the transaction is still active/current, and updates it once. The D1 update trigger records whole `before_json` and `after_json` snapshots with `action = 'update'`.
- `POST /w/:secret/api/splits/preview` and `POST /w/:secret/api/splits`
- `POST /w/:secret/api/batches/preview` and `POST /w/:secret/api/batches`
- `POST /w/:secret/api/imports/preview` and `POST /w/:secret/api/imports`
- `POST /w/:secret/api/offsets/preview` and `POST /w/:secret/api/offsets`
- `DELETE /w/:secret/api/transactions/:id`

Creation and update routes rely on D1 audit triggers. The endpoint must never insert a second manual audit row.

### Deletion semantics

For a transaction, use a **soft delete** by setting `is_deleted = 1` rather than physical `DELETE`:

- Standard ledger views exclude `is_deleted = 1`.
- The audit update trigger records `action = 'archive'` with full before/after rows.
- Restore is possible with `PATCH ... {"is_deleted": false}` only if product policy permits it; it logs `restore`.
- The audit UI calls this **Deleted from active ledger** rather than pretending the primary row was physically destroyed.

This is stronger than a physical delete in D1 because the primary record remains recoverable even if an audit migration later has a defect. If product requirements insist on physical deletion, use `DELETE` only after the audit triggers have been demonstrated in a local D1 test database; the delete trigger must capture every stored column.

### Response and failure behaviour

- Validate body size before parsing: default maximum 256 KB for JSON/CSV, 200 rows per batch/import unless product limits change.
- Return 400 for validation, 404 for missing/other-workspace objects, 409 for a stale reviewed draft or invalid current balance, 429 for rate limits, and 500 only for unexpected server errors.
- Never use a failed notification/event as a reason to report a successful D1 write as failed. There are no notifications in v1.
- Use opaque public error messages; log technical detail server-side without raw workspace secret or unredacted row snapshots.

## Financial rules retained from the existing tracker

### Direction invariant

Use explicit names in the new schema and UI:

- `creditor_person_id`: person who is owed
- `debtor_person_id`: person who owes
- positive amount: debt
- negative amount on the same direction: payment or offset

Every API, analytics query, review dialog, export, and test must agree. Assert the stored row, not only the review text.

### Splits

The payer can be outside the selected participants.

- All selected participants share the cost equally.
- If the payer is selected, they are excluded from debtors but remain in the divisor.
- If the payer is not selected, every selected participant owes their equal share to the payer.
- The review must show exact resulting ledger rows before confirmation.

### Offsets/netting

- Offset only truly reciprocal balances between two people in one currency.
- Calculate `min(A_owes_B, B_owes_A)` server-side at confirmation time.
- Write two negative entries—one in each direction—for the offset amount.
- Never create a single net-positive replacement debt.
- Use D1-safe concurrency protection. D1 does not offer Postgres advisory locks; use one batched/transactional statement per offset confirmation and return 409 if the recalculated reciprocal balance is no longer positive. Disable the browser confirmation button while pending and reload suggestions afterward.

### Imports

- Preview parses/validates raw CSV and writes nothing.
- Commit receives the raw CSV text and re-parses/revalidates server-side. Never accept browser-posted parsed row objects as the source of truth.
- Validate people, currencies, identical debtor/creditor, amount precision, row count, and body size.
- Batch operations must have a single review and one D1 transaction/batch.

- Reject a transaction that names an archived person/currency for a new record.
- Renaming a person changes only the current display label; historical audit snapshots preserve the exact previous label/id state captured at the time.

## Security and privacy

### Capability-link controls

- All workspace pages and APIs must verify the secret server-side.
- Set `Referrer-Policy: no-referrer` to avoid leaking the capability URL to external sites.
- Set `Cache-Control: no-store, private` on HTML and API responses under `/w/:secret`.
- Set restrictive CSP; do not use third-party scripts, analytics pixels, or remote fonts by default.
- Disable cross-origin CORS. This is a browser-sharing capability; it should not be callable from arbitrary origins.
- Validate origin for state-changing browser requests when an `Origin` header is present and matches the Worker origin. This is defense in depth; the capability remains the primary authorization mechanism.
- Do not redirect a request containing the secret to a URL that removes or exposes it.

### Rate limits and abuse

Implement lightweight Worker-side rate limits keyed by `workspace_id` plus a hashed client signal where practical. Rate-limit mutation endpoints more strictly than reads. Return 429 with retry guidance. This protects accidental double clicks and link leakage; it does not replace keeping the link private.

### Secrets

The initial project should require no application secret except optional deployment credentials managed by Cloudflare. It must have no `DATABASE_URL`, no `BOT_TOKEN`, no Telegram URL, no OpenRouter key, and no exposed D1 binding data in browser JavaScript.

## Testing requirements

### Test environment

- Every test uses a temporary/local D1 database created from the actual migrations.
- Never write to production D1 for tests.
- Do not test Telegram because Telegram does not exist in v1.
- Seed fixture helpers must create two workspaces to prove isolation.

### Required migration tests

1. Apply all migrations to blank D1 successfully.
2. Audit trigger: transaction create produces exactly one audit `create` entry with every expected stored transaction field.
3. Audit trigger: transaction update/archive produces exactly one appropriate audit entry with complete `before_json` and `after_json`.
4. Audit trigger: settings/person/currency/workspace mutations each produce an entry.
5. Audit lock: direct `UPDATE audit_log` and `DELETE audit_log` fail.
6. Secret hash never appears in `audit_log` JSON.
7. No `UPDATE`/`DELETE` API route targets `audit_log`.

### Required API tests

- invalid/missing workspace secret gets 404/403 without D1 mutation;
- a valid secret can only read/write its own workspace;
- all onboarding inputs validated; at least two people and one currency required;
- one active default currency invariant;
- archived people/currencies cannot make new transactions;
- preview endpoints produce no rows or audit entries;
- confirm endpoints produce expected ledger rows and matching audit rows;
- transaction edit preview produces no rows or audit entries; a confirmed edit produces one `update` audit row with complete before/after snapshots;
- CSV commit reparses the raw text, rejects tampered browser row data;
- deletion/archive carries full before/after audit snapshot;
- one offset confirmation writes exactly two negative records only when reciprocal balances remain;
- duplicate double-submit is rejected/idempotent;
- export contains only the requested workspace and can include audit records;
- no route references Telegram or outbound finance-event code.

### UI tests

Use jsdom for form/review/modal/payload tests and Playwright only where browser layout/accessibility behavior needs it.

Minimum UI coverage:

- onboarding validates and produces a shared link;
- no pre-onboarding hard-coded people/currencies are rendered;
- every write screen displays a review before its POST;
- transaction delete asks for confirmation;
- audit page clearly distinguishes create, update, archive, restore, and delete;
- settings mutation refreshes the active configuration;
- amount and currency are separate cells;
- mobile tables do not overflow unintentionally;
- no Telegram wording/configuration appears in UI or bundled source.

### Acceptance test for audit completeness

Make a table-driven test of all audited entity/action combinations. The test must fail when a new mutable table is added without a matching trigger contract. This is more valuable than source-pattern-only assertions.

### Delivery sequence

1. Run formatting, typecheck, focused tests, full migration test, then full test suite against local D1.
2. Deploy a preview Worker and apply migrations to a preview D1 database.
3. Create a throwaway preview workspace, exercise onboarding, one transaction, one setting mutation, archive/delete, audit read, and export.
4. Verify audit records against preview D1; then delete/abandon the preview workspace/database according to the test environment policy.
5. Create production D1 database and apply migrations only after preview verification passes.
6. Deploy production Worker.
7. Production smoke tests must be read-only except a deliberately created disposable production workspace if the user explicitly approves it. Do not write inside any real user workspace as a test.
8. Record deployed Worker URL, D1 migration version, commit SHA, and verification evidence in the release notes.

## Migration from the Vietnam tracker

This is a reuse-of-concepts project, not a direct data migration.

- Do not migrate the Vietnam trip ledger, members, currencies, `friends_finance` schema, Neon credentials, audit data, Telegram configuration, or bot source into the generic application.
- Reuse domain rules and UI/test patterns after translating them to workspace-scoped D1 queries and configurable ids.
- Translate `payee`/`payer` into clearer `creditor_person_id`/`debtor_person_id` names. Preserve the actual financial direction invariant.
- Replace fixed member constants with `workspace_people` queries.
- Replace fixed currency constants with active `workspace_currencies` queries and an appropriate minor-unit map.
- Recreate audit logic with D1 triggers and full JSON snapshots; do not copy Postgres trigger syntax or Neon tagged-template query code.
- Remove `finance-events.js`, bot calls, webhook tests, `FINANCE_EVENT_URL`, and Telegram-specific deployment ordering from the generic codebase.

## Definition of done

The reusable project is complete only when all of the following are demonstrably true:

- A new visitor can create a workspace by naming it, adding at least two people, choosing currencies, selecting a default currency, and confirming once.
- They receive one shareable capability link; a second browser using that link can read and edit the same workspace.
- The workspace can create and edit debt/payment/split/batch/import/offset records using review-before-write flows.
- The workspace can add, rename, archive, and restore people/currencies/settings without source edits.
- Every listed financial/configuration mutation appears in the audit page with a whole before/after snapshot as applicable.
- Direct application attempts to modify/remove audit rows fail.
- A person with only one workspace link cannot access another workspace’s records, settings, exports, or audit log.
- The first release contains no Telegram feature, secret, request, route, or UI copy.
- D1 migrations apply cleanly from blank database to current version.
- The full test suite passes on disposable/local D1 and no test writes to production data.
- The Worker is deployed with a documented preview-to-production path and production smoke verification.
